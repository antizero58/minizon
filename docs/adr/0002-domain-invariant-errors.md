# ADR 0002. Как домен сообщает о нарушении инвариантов

- Статус: предложено (ждёт «ок» владельца вместе с планом 0001)
- Дата: 2026-11-16
- Связано: docs/plans/0001-solution-scaffold-catalog.md, ADR 0003

## Контекст

Первый доменный класс — `Product` в сервисе Catalog (имя не пустое и не длиннее предела, цена строго больше нуля).
Нужно единое правило для всех сервисов: что делает фабрика/метод домена, когда ему передали недопустимые данные.
Данные придут снаружи (Gateway → gRPC → Application → Domain), поэтому нарушение инварианта — ожидаемый исход,
а не ошибка программиста. Верхние слои потом превратят его в ответ: ProblemDetails в Gateway, gRPC `INVALID_ARGUMENT` в сервисе.

Ограничение: Domain ни от чего не зависит (CLAUDE.md), значит сторонние библиотеки результатов в Domain не подходят.

Ограничение сборки (ADR 0003): `AnalysisLevel=latest-recommended` и `TreatWarningsAsErrors=true`. Предположительно
(требует проверки, план 0001, K6) это влияет на форму типа результата:
- статические методы `Result<T>.Success/Failure` внутри универсального типа отвергаются правилом CA1000
  («не объявляйте статические члены в универсальных типах»);
- тип с именем `Error` отвергается правилом CA1716 (совпадает с ключевым словом VB).

Поэтому форма ниже выбрана так, чтобы не задевать эти правила при любом исходе проверки: фабрики вынесены в непараметризованный
статический класс `Result`, тип ошибки называется `DomainError`. Подавлять правила не нужно.

## Варианты

### A. Исключения

Фабрика бросает `DomainException` (или `ArgumentException`), Application/Api ловит и превращает в ответ.

Плюсы:
- Минимум кода, привычно для .NET; невалидный объект не создаётся, проверку «нельзя забыть».
- Не нужен свой тип результата.
Минусы:
- Ожидаемый исход (ввод пользователя) идёт через исключения: дороже по производительности, поток управления читать сложнее,
  нужен глобальный обработчик с сопоставлением типов исключений.
- Естественно сообщается только первое нарушение, а не все сразу.
- Из сигнатуры не видно, что вызов может завершиться неуспехом.

### B. Собственный минимальный `Result<T>` с набором ошибок (рекомендуется)

`Product.Create(...)` возвращает `Result<Product>`: либо значение, либо непустой список `DomainError(Code, Message)`.
Конструктор `Product` закрыт, поэтому невалидный `Product` создать нельзя. Тип лежит в Domain каждого сервиса
(общей библиотеки между сервисами нет).

Плюсы:
- Неуспех — часть сигнатуры; исключения остаются для настоящих ошибок (баги, нарушение контракта метода).
- Возвращаются все нарушения за один вызов; у каждой ошибки стабильный код (`product.name.empty`) — удобно сопоставлять с ProblemDetails
  и gRPC, не разбирая текст сообщений.
- Unit-тесты проще: проверка значения и кодов, без `Assert.Throws`.
Минусы:
- Свой тип (несколько десятков строк) и дисциплина: обращение к `Value` у неуспешного результата бросает `InvalidOperationException`.
- Фабрики результата живут в отдельном непараметризованном классе `Result` (из-за CA1000), это чуть менее привычно.
- Дублирование типа, когда он понадобится в другом сервисе; общий «shared kernel» — отдельным ADR, когда дублирование станет реальным.

### C. Библиотека (ErrorOr, FluentResults)

Плюсы: готовый, отработанный API. Минусы: внешняя зависимость в Domain — противоречит правилу «Domain ни от чего не зависит»
и тесту слоёв из ADR 0003; лишняя поверхность API. Отклонён.

## Решение (рекомендация)

Вариант B.

Форма типов (в Domain сервиса, папка `Common`):
- `DomainError` — неизменяемая запись с полями `Code` и `Message` (строки).
- `Result<T>` (где `T : notnull`) — неизменяемый результат: `IsSuccess`, `IsFailure`, `Value` (бросает `InvalidOperationException` при неуспехе),
  `Errors` (`IReadOnlyList<DomainError>`, пустой при успехе). Открытого конструктора нет.
- `Result` — статический класс с фабриками `Success<T>(T value)` и `Failure<T>(IReadOnlyList<DomainError> errors)`.
  `Failure` с пустым списком или `null` — нарушение контракта метода, бросает `ArgumentException`/`ArgumentNullException`.
- Результат без значения (для методов-команд) в этой задаче не нужен и не делается. Когда понадобится, `Result` становится
  нестатическим классом с экземплярами «успех/неуспех» и теми же статическими фабриками (CA1000 к неуниверсальному типу не относится);
  для вызывающих это совместимое изменение.

Правила:
1. Фабрики и методы доменных сущностей, принимающие внешние данные, возвращают `Result<T>`.
2. Коды ошибок: `<сущность>.<поле>.<причина>` в нижнем регистре, слова в причине через `_` (например, `product.name.too_long`).
   Константы лежат рядом с сущностью (например, `ProductErrors`). Коды — публичное поведение: меняются только вместе с потребителями.
   Сообщения (`Message`) — на английском, для логов и разработчиков; клиенты опираются на код, а не на текст.
3. Параметры, принимающие внешний ввод, объявляются nullable (`string?`): `null` — обычная ошибка валидации, а не `ArgumentNullException`.
4. Фабрика проверяет все инварианты и возвращает все нарушения сразу; одно нарушение — одна ошибка (код не повторяется).
5. Исключения в домене — только для нарушений контракта внутри кода (обращение к `Value` у неуспешного результата, `Failure` без ошибок).
6. Перевод `DomainError` в ответ API/gRPC — в задачах, где появятся вызывающие эндпоинты, не в этой.

## Последствия

- В Domain Catalog появляются `Result`, `Result<T>`, `DomainError` (папка `Common`).
- Если владелец выберет A: в плане 0001 правится раздел «Domain» (фабрика бросает `DomainException`, тесты на `Assert.Throws`);
  остальной план не меняется.
- Применимо к будущим сущностям всех сервисов; пересматривается, если появится общая библиотека с Result.
