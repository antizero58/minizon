# ADR 0003. Каркас решения, правила сборки и проверка границ слоёв

- Статус: принято 2026-11-16 вместе с планом 0001
- Дата: 2026-11-16
- Связано: docs/plans/0001-solution-scaffold-catalog.md, ADR 0001, ADR 0002

## Контекст

Нужен каркас, на который лягут все следующие сервисы: файл решения, общие свойства сборки, управление версиями пакетов,
правила анализаторов, соглашения об именах проектов и способ проверять, что слои зависят друг от друга только в разрешённом
направлении (Domain → Application → Infrastructure → Api, Domain ни от чего не зависит).

Среда: Windows, .NET SDK 10.0.302. Хук проверки (.claude/hooks/verify.sh) запускает `dotnet build` и `dotnet test` в корне
репозитория без указания решения. Хук срабатывает, только если среди изменённых файлов есть `*.cs`, `*.csproj`, `*.props`, `*.targets`
или `*.proto`; изменения только в `.slnx`, `global.json` или `.editorconfig` его не запускают (см. «Последствия»).

Утверждения ниже с пометкой «требует проверки» не подтверждены; процедуры проверки — в плане 0001 (идентификаторы K1–K11).

## Решения

### 1. Формат решения: `Minizon.slnx` в корне

Варианты:
- (a) `.sln` — классический формат: поддерживается всеми инструментами, но нечитаемый diff и частые конфликты слияния (GUID проектов);
- (b) `.slnx` — XML-формат, поддерживается SDK 10 (рекомендуется): короткий читаемый файл, меньше конфликтов; нужен CLI/IDE с поддержкой.

Выбран (b). Предположение (требует проверки, K2): `dotnet build` и `dotnet test` в корне подхватывают единственный `.slnx` без указания пути.
Правило: в корне не держать `.sln` и `.slnx` одновременно (команда без пути станет неоднозначной) и не держать в корне `*.csproj`.

### 2. Именование и размещение проектов

Варианты:
- (a) короткие имена `Catalog.Domain`: меньше шума, но возможны конфликты пространств имён с общими клиентами и Gateway;
- (b) префикс `Minizon.` (рекомендуется): длиннее, но однозначно.

Выбран (b):
- сервисы: `src/Services/<Сервис>/Minizon.<Сервис>.<Слой>/Minizon.<Сервис>.<Слой>.csproj`, где `<Слой>` — `Domain`, `Application`,
  `Infrastructure` или `Api`; пространство имён по умолчанию совпадает с именем проекта;
- тесты сервиса: `tests/Minizon.<Сервис>.<Вид>Tests/` (например, `Minizon.Catalog.UnitTests`, `Minizon.Catalog.ApiTests`);
- общие тесты архитектуры: `tests/Minizon.ArchitectureTests/` — одни на все сервисы.

### 3. Общие свойства сборки: Directory.Build.props

Варианты строгости:
- (a) только `Nullable` и анализаторы по умолчанию, предупреждения не ошибки: предупреждения копятся, это противоречит правилу «не отключать проверки»;
- (b) `TreatWarningsAsErrors=true` всегда + `AnalysisLevel=latest-recommended` (рекомендуется);
- (c) как (b), но предупреждения как ошибки только в CI/Release: расхождение «у агента собралось, в CI нет», а хук собирает Debug.

Выбран (b). Состав: `TargetFramework=net10.0`, `Nullable=enable`, `ImplicitUsings=enable`, `TreatWarningsAsErrors=true`,
`AnalysisLevel=latest-recommended`. В Directory.Build.props нет `PackageReference` и `NoWarn`.

Предположение (требует проверки, K6): режим `latest-recommended` включает правила, которые влияют на форму кода, в том числе
CA1000, CA1716 (см. ADR 0002) и CA1707 (подчёркивания в именах). Если какое-то из них не включено — это не ошибка каркаса,
но форму типов из ADR 0002 всё равно не меняем.

Исключение для аудита NuGet. Варианты:
- (a) оставить NU1901–NU1904 ошибками, как всё остальное: строго, но сборка «краснеет» без единого изменения в репозитории,
  когда в базе уязвимостей появляется запись, и блокирует все задачи до обновления пакета;
- (b) перевести NU1901–NU1904 в предупреждения через `WarningsNotAsErrors` (рекомендуется): сборка не ломается внезапно,
  но предупреждение обязано быть исправлено обновлением пакета в том же или ближайшем изменении; ревьюер проверяет, что их нет.

Для О3 принят рекомендованный вариант (b), см. план 0001. Основная сессия подтвердила K8 во временном проекте с SDK 10.0.302,
NuGet.org и `Newtonsoft.Json` 12.0.1.
С `WarningsNotAsErrors` сборка выдала предупреждение `NU1903` и код выхода `0`. Без `WarningsNotAsErrors` сборка выдала ошибку
`NU1903` и код выхода `1`.

Сторонние анализаторы (Sonar, Meziantou, StyleCop) не подключаем: встроенных достаточно на старте. Анализаторы xUnit приходят с пакетом
`xunit.v3.mtp-off` и тоже работают как ошибки.

### 4. Центральное управление версиями пакетов: Directory.Packages.props

Варианты:
- (a) версии в каждом csproj: проще на старте, но разъезжаются между сервисами;
- (b) `ManagePackageVersionsCentrally=true`, `PackageReference` в проектах без `Version` (рекомендуется).

Выбран (b). `GlobalPackageReference` не используем: он добавил бы пакет и в Domain. Domain не имеет ни одной `PackageReference`
(проверяется тестом архитектуры, решение 6).

### 5. global.json

Варианты:
- (a) без global.json: каждый агент/CI собирает тем SDK, что установлен; поведение `dotnet test` различается между версиями SDK (ADR 0001);
- (b) `sdk.version=10.0.302`, `rollForward=latestPatch`, `allowPrerelease=false` (рекомендуется): допускаются только патчи полосы 10.0.3xx,
  поведение `dotnet test` воспроизводимо;
- (c) то же с `rollForward=latestFeature`: допускается 10.0.4xx и выше — удобнее, но черновик ошибочно называл это «фиксацией SDK».

Выбран (b). Секции `test.runner` нет. Принятый вариант C из ADR 0001 использует xUnit v3 с отключённым MTP в режиме VSTest.

### 6. Проверка направления зависимостей

Варианты:
- (a) только ссылки `ProjectReference` и ревью: Domain без ссылок физически не видит другие слои (ошибка компиляции); остальное держится на внимательности;
- (b) библиотека архитектурных тестов (NetArchTest, ArchUnitNET): проверяет использование типов, но это новая зависимость, а в пустых
  проектах проверять нечего;
- (c) тест без внешних зависимостей, читающий csproj (рекомендуется).

Выбран (c). Тест `tests/Minizon.ArchitectureTests` находит корень репозитория (каталог с `Minizon.slnx`), перебирает все csproj в
`src/Services/*/` и для каждого:
- определяет слой по имени `Minizon.<Сервис>.<Слой>`; проект с другим именем — ошибка (неизвестный слой);
- разрешает пути прямых `ProjectReference` относительно каталога ссылающегося проекта и сравнивает полные нормализованные пути
  с путями канонических `.csproj` своего сервиса: Domain — нет; Application — Domain; Infrastructure — Application;
  Api — Application и Infrastructure (Api — точка композиции, DI подключает Infrastructure). Одноимённый проект вне каталога
  сервиса не проходит проверку;
- для Domain дополнительно: нет `PackageReference`, нет `FrameworkReference`, SDK — `Microsoft.NET.Sdk`; сборка Domain ссылается только на
  сборки платформы (`System*`, `netstandard`, `mscorlib`);
- если не найдено ни одного проекта сервиса — тест падает (защита от «тихо ничего не проверил»).

Ограничение: проверяются прямые ссылки; транзитивные (Api видит Domain через Application) допускаются, использование типов в обход
слоёв ловит ревью. Когда слоёв и сервисов станет много, перейти на (b) отдельным ADR.
Предположение (требует проверки, K7): тест красный, если в Api добавить прямую ссылку на Domain или в Domain — любой `PackageReference`.

### 7. Анализатор и имена тестов (CA1707)

`latest-recommended` предположительно (требует проверки, K6) отвергает подчёркивания в именах публичных методов, а тестовые методы xUnit публичные
(`Create_WithEmptyName_ReturnsError`). Варианты:
- (a) имена тестов без подчёркиваний (`CreateWithEmptyNameReturnsError`): ничего не ослабляем, но длинные имена хуже читаются;
- (b) отключить только CA1707 только в tests/ через `tests/.editorconfig` (рекомендуется): правило предназначено для публичного API
  библиотек, а не для тестов; Directory.Build.props и src/ остаются строгими;
- (c) отключить глобально — отклонено.

Для О2 принят рекомендованный вариант (b), см. план 0001. Других подавлений в tests/ без отдельного решения не делается.

## Последствия

- Все следующие сервисы повторяют схему папок и имён; общие свойства наследуются из Directory.Build.props; тест архитектуры
  проверяет их автоматически.
- Новый пакет = запись в Directory.Packages.props + ссылка без версии в проекте.
- Предупреждения сборки считаются ошибками. Для NU1901–NU1904 применяется утверждённое исключение.
- Правка списка разрешённых ссылок в тесте архитектуры — архитектурное решение, проходит через ADR и ревью.
- Хук не реагирует на изменения только в `.slnx`, `global.json`, `.editorconfig`. Предложение владельцу (вне этой задачи): добавить эти
  расширения в регулярное выражение хука.
