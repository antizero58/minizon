# ADR 0001. Тестовый фреймворк и раннер для бэкенда

- Статус: принято (владелец выбрал вариант C 2026-11-16, после проверки Шага 0 плана 0001)
- Дата: 2026-11-16
- Связано: docs/plans/0001-solution-scaffold-catalog.md, ADR 0003, .claude/hooks/verify.sh

## Контекст

CLAUDE.md задаёт стек тестов бэкенда: «xUnit + Testcontainers». Версия xUnit не выбрана. Хук проверки
(.claude/hooks/verify.sh, строки 62–63) после каждой остановки агента запускает в корне репозитория ровно две команды:

```
dotnet build --nologo -v q
dotnet test --no-build --nologo --filter "Category!=Integration"
```

Среда: Windows, .NET SDK 10.0.302, Docker не запущен. Интеграционные тесты (нужен Docker) помечаются
`[Trait("Category","Integration")]` и в хуке не запускаются.

Известная проблема (сообщил владелец): на SDK 10.0.302 `dotnet test` для xUnit v3 в режиме Microsoft Testing Platform (MTP)
сообщает «запущено ноль тестов» и возвращает код 5, хотя тестовый exe при прямом запуске работает.

В SDK 10 у `dotnet test` два режима: VSTest (по умолчанию) и MTP (включается секцией `"test": { "runner": "Microsoft.Testing.Platform" }`
в global.json). У них разный синтаксис фильтра: `--filter "Category!=Integration"` — синтаксис VSTest; у xUnit v3 в MTP свои параметры
(`--filter-trait`, `--filter-not-trait`, `--filter-query`).

### Гипотезы (все требуют проверки)

Черновик этого ADR ссылался на опыты «на минимальных проектах». Их результаты ничем не подтверждены, поэтому ниже они записаны
как гипотезы. Каждая проверяется процедурой из плана 0001 (раздел «Шаг 0», идентификаторы V0–V3); основная сессия заносит
фактический результат в таблицу «Результаты проверки» в конце этого ADR.

- Г1 (требует проверки, V1). xUnit v2 (`xunit` 2.9.x, `xunit.runner.visualstudio`, `Microsoft.NET.Test.Sdk`) в режиме VSTest
  выполняет команду хука как есть: тест без трейта выполняется, тест с `Category=Integration` исключается, код 0;
  падающий тест даёт код 1; работает и в решении `.slnx` из нескольких тестовых проектов.
- Г2 (требует проверки, V1). В режиме VSTest фильтр, под который не попал ни один тест, даёт код 0 (только предупреждение в выводе),
  то есть хук «ноль тестов» не замечает.
- Г3 (требует проверки, V2). Причина «ноля тестов» в режиме MTP — аргумент `--nologo` из хука: `dotnet test` в режиме MTP передаёт
  незнакомый аргумент тестовому приложению, оно его отвергает, и `dotnet test` сворачивает это в «ноль тестов», код 5.
  Без `--nologo` тесты выполняются.
- Г4 (требует проверки, V2). В режиме MTP xUnit v3 исключает Integration-тесты по `--filter-not-trait "Category=Integration"`.
  Работает ли там же VSTest-синтаксис `--filter "Category!=Integration"` — неизвестно.
- Г5 (требует проверки, V2). В режиме MTP запуск, в котором не выполнен ни один тест, завершается ненулевым кодом (по документации MTP — 8).
- Г6 (требует проверки, V3). xUnit v3 без секции `test.runner` в global.json, но с включённой в проекте поддержкой MTP, падает с ошибкой
  вида «Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later»;
  xUnit v3 с отключённым MTP (пакет `xunit.v3.mtp-off` 4.0.3 + `xunit.runner.visualstudio` 4.0.1 + `Microsoft.NET.Test.Sdk` 18.12.0) работает в режиме VSTest
  с командой хука как есть. Существование и поведение пакета `xunit.v3.mtp-off` тоже требует проверки.

## Варианты

### A. xUnit v2 + VSTest

Пакеты: `xunit` 2.9.x, `xunit.runner.visualstudio`, `Microsoft.NET.Test.Sdk`. Фильтр `--filter "Category!=Integration"`. Хук и CLAUDE.md не меняются.

Плюсы:
- Команда хука и команды из CLAUDE.md не меняются (при условии, что подтвердится Г1).
- Стандартные флаги `dotnet test` (`--nologo`, `--logger`, `--filter`) работают; агенты не наткнутся на «ноль тестов» из-за привычного флага.
- Самый распространённый путь: Testcontainers и WebApplicationFactory давно работают с xUnit v2 в VSTest.
Минусы:
- xUnit v2 в режиме сопровождения, новые возможности (например, `TestContext.Current`) только в v3.
- Миграция на v3 позже потребует правок пакетов и, возможно, хука.
- Тихий успех при нуле выбранных тестов (если подтвердится Г2): хук не отличит «тесты прошли» от «тестов не нашлось».

### B. xUnit v3 + MTP, правка хука

Пакет `xunit.v3`; тестовые проекты — exe; в global.json `"test": { "runner": "Microsoft.Testing.Platform" }`.
В хуке строка 63 становится `dotnet test --no-build --filter-not-trait "Category=Integration"` (без `--nologo`, фильтр в синтаксисе xUnit v3);
соответственно меняются команда «Быстрые тесты» и правило про фильтр в CLAUDE.md и строка про фильтр в .claude/agents/test-writer.md.

Плюсы:
- Актуальная ветка xUnit; MTP — направление развития тестирования в .NET.
- Если подтвердится Г5, ноль выполненных тестов — ненулевой код, хук это заметит.
- Тестовый проект — самостоятельный exe, запускается напрямую.
Минусы:
- Правка хука, CLAUDE.md и инструкции test-writer (файлы вне зоны architect; меняет основная сессия с «ок» владельца).
- Ловушка на весь проект (если подтвердится Г3): любой незнакомый MTP аргумент `dotnet test` (включая привычный `--nologo`) даёт код 5
  и «ноль тестов» без понятной причины в выводе.
- MTP включается для всего решения через global.json; смешивать с VSTest-проектами нельзя.
- Если подтвердится Г5: тестовый проект, в котором есть только Integration-тесты, уронит хук кодом «ноль тестов»; понадобится
  `--ignore-exit-code 8` или правило «в каждом тестовом проекте есть быстрые тесты».

### C. xUnit v3 в режиме VSTest (MTP отключён) — принят

Пакеты: `xunit.v3.mtp-off`, `xunit.runner.visualstudio` (проверено с 4.0.1), `Microsoft.NET.Test.Sdk`. Секции `test.runner` в global.json нет. Хук и CLAUDE.md не меняются.

Плюсы:
- Актуальный xUnit v3 при неизменном хуке и тех же командах, что в варианте A.
- Переход на MTP позже — замена пакета и global.json, без переписывания тестов.
Минусы:
- Менее проторённая конфигурация, чем A (Г6 подтверждена, см. «Результаты проверки»).
- Режим VSTest и его тихий успех при нуле тестов (как в A).
- Тестовые проекты — exe; поведение в IDE (Visual Studio, Rider) не проверено.

Отклонено сразу: NUnit и MSTest — расходятся с CLAUDE.md («xUnit»), инструкции агентов написаны под xUnit.

## Решение

Вариант C: xUnit v3 с отключённым MTP (`xunit.v3.mtp-off`) в режиме VSTest; хук и CLAUDE.md без изменений.
Выбрал владелец после проверки Шага 0. Проверено (см. «Результаты проверки»): команда хука выполняет тесты в решении `.slnx`
из нескольких проектов, в том числе тест через WebApplicationFactory, и исключает Integration-тесты; без фильтра падающий тест даёт код 1.
Вариант A тоже рабочий, но это xUnit v2 в режиме сопровождения. Вариант B требует правки хука и CLAUDE.md и ломается на привычном `--nologo`.

Переход на MTP (вариант B) — отдельным ADR: замена `xunit.v3.mtp-off` на `xunit.v3`, global.json, хук, CLAUDE.md.

Библиотека утверждений: стандартный `Assert` xUnit, без FluentAssertions/Shouldly. Причина: меньше зависимостей,
у FluentAssertions с 8-й версии коммерческая лицензия. Если понадобится выразительнее, вернёмся отдельным решением.

Версии пакетов фиксируются в Directory.Packages.props (ADR 0003). Проверены: xunit.v3.mtp-off 4.0.3,
xunit.runner.visualstudio 4.0.1, Microsoft.NET.Test.Sdk 18.12.0, Microsoft.AspNetCore.Mvc.Testing 10.0.15.

## Последствия

- Тестовые проекты: `<OutputType>Exe</OutputType>` (требование xUnit v3), `IsPackable=false`; `xunit.runner.visualstudio` с `PrivateAssets=all`.
  В тестах доступен `TestContext.Current` (например, `TestContext.Current.CancellationToken`).
- Все тесты, которым нужен Docker, обязаны иметь `[Trait("Category","Integration")]`. Тесты в памяти (например, WebApplicationFactory без
  внешних зависимостей) трейта не получают и идут в быстром прогоне.
- Тихий успех при нуле выбранных тестов хук не обнаруживает (если подтвердится Г2). Поэтому критерии готовности каждой задачи
  включают проверку, что число выполненных тестов больше нуля и что нарочно падающий тест даёт ненулевой код (процедура — в плане 0001).
  Доработку хука (например, разбор итоговой строки) владелец может заказать отдельной задачей.
- Переход на MTP позже затронет: пакеты, global.json, хук, CLAUDE.md, инструкцию test-writer.
